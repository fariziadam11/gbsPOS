# Frontend Preferences

- Prefers shadcn UI (shadcn-svelte or shadcn/ui) over component libraries like PrimeVue; explicitly asked to remove PrimeVue dependencies. Confidence: 0.9
- Responsive UI/layout on every page and dialog is a hard requirement, not optional polish. Confidence: 0.8
- Redesigns/refactors should keep the project's existing Tailwind setup and runtime (bun). Confidence: 0.7
- For Android Jetpack Compose UI/UX work, follows the repo's existing design system (e.g., design-system/MASTER.md palettes) and established module theme patterns (e.g., Material3 + kiosk scale like fuelpos) rather than inventing new design tokens — "don't reinvent". Confidence: 0.7
- Designs for touch/kiosk contexts (payment terminals, POS): ≥48dp touch targets, large display typography for amounts, and explicit state/status cards with loading and error states. Confidence: 0.6
- In kiosk/POS UIs, never show a loading spinner in idle states — anything that reads as "busy/loading" while idle (e.g., a spinning Sync icon in the disconnected state) must be replaced with a static state icon; spinners should only appear while a transaction is actually processing. Transient UI like spinners must be driven only by the local device's card-transaction action, never by a server/broadcast "PROCESSING" status (e.g., a stale or other-device pending transaction) — user reported the spinner again even after the idle fix. Confidence: 0.9
- Payment result screens (success and failure) must include a dismiss/"Selesai" action that resets the UI back to the waiting-for-payment state so the cashier can immediately process the next transaction. Confidence: 0.8
- Payment flows are device-specific: on the Sunmi D3 Pro (cashier/terminal) the payment flow lives in the cashier screen + payment dialog (CartScreen → PaymentDialog → onLaunchCardPayment), while the checkout screen is only for phones. When aligning a payment flow with the reference app, verify the correct device-specific screen/flow instead of assuming checkout screen. Confidence: 0.85
- Failed or errored transactions must never appear as "payment successful" in the history/receipt UI — they stay visible in history but carry an explicit "Gagal" status label (and a failed receipt, not "Pembayaran berhasil"). Do NOT simply filter them out: a failed CARD order is identified by a missing `transactionId`, and filtering by `isVoided` alone is wrong because a void is a distinct concept. Confidence: 0.85
- Payment status shown in the UI (receipt/history) must be driven by the live, authoritative source — the WebSocket payment status — never by stale in-memory order snapshots; inference heuristics (e.g., missing `transactionId`) are only valid for server-loaded data. The user reports it as a bug when a successful transaction is mislabeled "failed" on the receipt while history (fresh from server) shows success. Confidence: 0.8
- Multi-device card payment flows must be single-action end-to-end: pressing the pay button once on the initiating device (pos-web "Bayar dengan Kartu") should propagate automatically through the companion app straight into the SoftPOS app, with no extra confirmation tap on intermediate devices. Companion apps should auto-start the card transaction as soon as the WAITING state arrives (guarding against double-launch) rather than showing a "Mulai transaksi kartu" button — the user explicitly called the extra companion button press redundant. Confidence: 0.85
